- **Idea (Nick): save only frames, not whole videos.** Saving every frame as
  its own picture would not save space (the video is already one JPEG per
  frame). What would: record at full rate only while a robot is running
  (run_sheet already tells the Pi when each run starts and ends), and at a
  low rate (e.g. 1 to 2 fps) while marks are being measured. Runs are about
  10 s and measuring about 2 min, so this cuts the size by roughly 80 to 90%.
  Also: camrec checks free space before and during recording, warns early,
  and closes the file cleanly when space runs low; preflight reports the Pi's
  free space and hours of recording left.
- **Refined (Nick): keep only significant frames.** camrec keeps a frame
  when it matters: every frame from each run's start note to its end note
  (robot moving, start flash and blink code); any frame where the picture
  changes beyond the camera's own noise (frame differencing on a small
  grey copy; a hand placing a robot, a robot moving outside a run); one
  frame at each note (marks typed); and one frame every few seconds as a
  heartbeat so the timeline has no long gaps. frames.csv keeps the true
  frame number and time of each kept frame, so the analysis tools still
  line frames up with the robot logs. Expected size: a few percent of
  tonight's. Test: replay tonight's full recording through the filter and
  check every run's blink pairs and start/end frames survive.
- **T1 run 1 (Left, square3, BF27-2): ended 47.7 cm from start, turned
  +79 deg (left).** The robot's own wheel odometry put it 58.3 cm off, so it
  knew it hadn't come back: the turns themselves were off, not the wheels
  slipping. The square's turns are IMU-targeted (start + 90 deg x k), so the
  IMU's yaw under-read real rotation by about 7% (79 deg over 1080 deg of
  turning, about 6.6 deg extra per corner), or drifted about 0.6 deg/s.
  Camera will separate scale from drift (calibration spins: 720 deg each way).
  If scale: a gyro scale parameter, set from the calibration spin + camera,
  is the fix (new test: spin N turns on camera, compare IMU yaw).
- **Idea (Nick): dock-based self-calibration loop.** The robot starts in a
  3D-printed home that presses its two nose switches, drives out and back on
  a route that grows each run, and compares when it expected to reach home
  with when the switches actually close (and which one closes first). Each
  run corrects the next, until the error is small enough for production.
  Notes for the design:
  - Out-and-back on the same line hides wheel-size errors (they cancel both
    ways). Use loops that don't retrace (square, circle, figure 8) so the
    return error shows gyro scale, wheel mismatch and wheel size.
  - Two switches give: distance error along the approach (switch time vs
    expected), heading error (time between the two switches), not lateral
    offset if the dock funnels the robot in. Option: a wider mouth with a
    third switch or a printed scale under the camera.
  - Growing routes: start short (bounded error, no edge risk), lengthen once
    the last run's error is below a threshold.
  - Measures the robot's own consistency, not absolute position on the
    floor: the camera (or tape) stays the independent referee for the
    project's accuracy claims; the dock replaces tape for routine calibration.
  - Fits the plug-and-play goal: the dock is also where a production robot
    parks and charges.
  New tests: dock repeatability (place 20 times, switch timing spread);
  dock-calibrated gyro scale and wheel sizes vs camera-measured; end error
  of T1 routes before and after dock calibration.
- **Dock loop, refined (Nick):** progression from straight out-and-back
  (checks the switches and the return, bounded risk), to gentle curves, to
  small loops, to full squares, growing only after the last run came home
  within a threshold, so a bad parameter never causes a catastrophic miss.
  **Live camera during the loop:** tools/live/track_live.py (our tracker,
  so far tested on simulated video only) watches each calibration run in
  real time: a safety stop if the robot heads for an open edge or will miss
  the dock; the error measured along the whole path, not only at home, so
  each run teaches more and fewer runs are needed. Design so the dock-only
  loop still works where a site has no camera. New test: track_live on the
  real camera (fix rate, latency, position error vs tape) before relying on
  it as a guard.

## Afternoon: per-robot corrections (firmware 2026-10-20b)

- **Turn over-shoot: scale or drift? Not settled.** The squares' ~80 deg over 1080 deg of
  turning fits a gyro scale (x1.075) and a gyro drift (~0.6 deg/s over a ~100-140 s square)
  equally well. The L route ended +9 deg with no net turning commanded (right 90, then back):
  a pure scale error cancels there, drift does not, so drift is the likelier cause. The
  straights can't tell (library move() steers on the wheels, not the gyro). Tests that
  decide it: `run gyro` (stand still 30 s: drift shows as a creeping heading) and the
  camera's calibration spins (calib.py's gyro_scale from last night's video).
